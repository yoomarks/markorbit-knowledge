# Obsidian Vault-origin Staging Verification V1

## Purpose

K11 adds a dedicated verification and finalization boundary for Markdown that entered Knowledge through the reviewed Vault import path established by K08–K10.

The boundary exists because a Vault-authored document has different provenance from a document generated by the governed Converter/Worker pipeline. K11 must therefore verify imported bytes without inventing a `ConversionRun`, `Worker`, `RawArtifact`, conversion attempt or upload grant.

## Input truth

K10 persists `VaultOriginStagingDocumentV1` with status `IMPORTED_UNVERIFIED` and a content-addressed Markdown copy under the shared Staging CAS root.

K11 treats that K10 record and its CAS bytes as the immutable input. Verification does not re-read the live Vault path, does not require the current Vault Binding, and does not require `MARKORBIT_OBSIDIAN_VAULT_ROOT` to be configured.

The K10 document itself remains immutable and remains `IMPORTED_UNVERIFIED`. K11 records new evidence alongside it rather than rewriting its origin history.

## Verification contract

`VaultOriginStagingVerificationEvidenceV1` is produced by the locked verifier:

```text
builtin-vault-origin-staging-verifier@1.0.0
```

The verifier checks the immutable CAS copy for:

- CAS hash and byte-size integrity through the K10 Staging repository;
- valid UTF-8;
- absence of NUL bytes;
- bounded frontmatter structure when a frontmatter block is present;
- rejection of YAML aliases, anchors, tags and merge keys at this boundary;
- absence of user-authored `markorbit.*` / `markorbit:` reserved provenance claims;
- presence of a Markdown body, with an empty body recorded as a warning rather than fabricated content.

Outcomes are:

- `PASS` — all required checks pass;
- `PASS_WITH_WARNINGS` — required checks pass but non-fatal warnings exist;
- `FAIL` — at least one required check fails.

A document receives at most one immutable verification decision. Exact idempotency replay returns the original evidence; a different later attempt cannot silently replace it.

## Reserved provenance namespace

Vault-authored Markdown is external input. It must not be able to claim internal MarkOrbit provenance by supplying frontmatter such as:

```yaml
markorbit.workspaceId: ...
markorbit.conversionRunId: ...
```

Such content fails `MARKORBIT_RESERVED_NAMESPACE_CLEAR`. K11 does not reinterpret or overwrite those claims because doing so would blur the trust boundary; the imported copy is instead finalized as blocked.

## Finalization contract

`VaultOriginStagingFinalizationV1` binds one immutable verification to the exact imported document and content hash.

Decision mapping is deterministic:

```text
PASS / PASS_WITH_WARNINGS -> VERIFIED
FAIL                      -> BLOCKED
```

Finalization is append-only evidence. It does not mutate the K10 document status and does not require CAS or Vault filesystem access once verification evidence is durable. Exact idempotency replay returns the original finalization.

## Persistence

Migration `0027_vault_origin_staging_verification` adds:

- `vault_origin_staging_verifications`;
- `vault_origin_staging_verification_idempotency`;
- `vault_origin_staging_finalizations`;
- `vault_origin_staging_finalization_idempotency`.

The tables reference the dedicated K10 `vault_origin_staging_documents` ledger and remain separate from conversion-generated `staging_documents` and `staging_document_verifications`.

## Explicit non-goals

K11 does not:

- create or fake Converter/Worker/RawArtifact provenance;
- copy the imported document into conversion-generated Staging tables;
- make a `VERIFIED` Vault-origin document ReadyPackage-eligible;
- create or deliver a ReadyPackage;
- mutate MarkOrbit Core;
- perform semantic interpretation, classification, summarization or other AI work;
- poll the Vault, synchronize changes, merge conflicts, overwrite files or propagate deletions.

A later milestone may define a provenance-preserving normalization or promotion gate from `VERIFIED` Vault-origin content into a canonical downstream path. That gate must keep the Vault-origin evidence chain explicit and must not fabricate a `ConversionRun` merely to satisfy existing downstream schemas.
